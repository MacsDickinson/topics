# Contributing

For UI work, follow the [design system](design-system.md), including its same-change requirement for missing tokens, components, states and patterns.

## Crates and dependency direction

- `topics-core`: foundation document/search values plus canonical workspace wire values and deterministic UUID/date/candidate validation. It has no filesystem, SQL, UI or network behavior.
- `topics-store`: `TopicsService` for source traversal/configuration/index/watch plus `WorkspaceService` for scoped discovery proposals, authoritative Markdown knowledge and recoverable writes. It depends on core and owns note access and app-data persistence.
- `topics-cli`: argument handling and JSON presentation over the same service and shared `application_data_dir()` resolver.
- `topics-bdd`: explicit Cucumber steps using the services and synthetic source-tree snapshots. Separate Phase 0 and workspace runners use `fail_on_skipped`; the workspace evidence maps four presentation/protocol-owned scenarios to the other streams.
- `topics-runtime`: pinned Codex app-server integration and the scoped MCP service, with protocol validation, cancellation and publication permits. Its host interface uses core values; desktop supplies the store adapter.
- `apps/desktop`: the Tauri 2 workspace member in `apps/desktop/src-tauri`, with React/TypeScript presentation. Its real IPC calls store services; it does not duplicate persistence or parsing.

Dependencies point inward from CLI/desktop/BDD to store to core. Runtime also depends on core; store does not depend on runtime. Neither store nor core knows about Tauri or React. Phase 0 remains the search foundation; the topic-workspace milestone adds claims, reviewed discovery, MCP and correction chat. Task management remains a later milestone.

## Search from UI to Markdown

The desktop resolves app data with `topics_store::application_data_dir()`. A resolver error remains managed application state, so an attempted search displays the error in a usable window rather than aborting or falling back. On the first valid search it creates a service and retains a `WatchHandle`. Blocking store work runs through Tauri's `spawn_blocking`, off the WebView event loop.

`TopicsService::open(app_data_dir)` prepares/canonicalizes app data **without scanning notes**. The first data read performs a full content-hash scan of the currently selected root; an explicit `index()` also always hashes content. Consequently, an unavailable old root does not prevent `use_notes_root` or `init_notes_root` from configuring a replacement. Search/people/documents report actionable errors for no root, an unavailable root or invalid config; these conditions are not empty search results.

The IPC command calls `service.search(&query)` and returns title, root-relative path and snippet. Serde carries owned values to React. The desktop adapter turns store failures into message rejections displayed by the existing error UI. The frontend debounces requests, ignores obsolete responses, and displays No matches only after a successful empty response.

Query terms are bound parameters and literal FTS terms, with punctuation-only terms omitted and NUL treated as a separator. FTS chooses the best excerpt column, including title-only matches. Snippets contain exact `<mark>` highlight tokens and untrusted source text; the React renderer emits text nodes for note content and only creates highlight elements for those tokens. It does not insert raw note HTML. The focused browser test verifies hostile title/snippet markup creates no injected image/script elements and executes nothing while highlighting still works. Literal-mark cosmetic behavior is deferred.

## Service usage and root changes

```rust,ignore
let app_data_dir = topics_store::application_data_dir()?;
let mut service = topics_store::TopicsService::open(app_data_dir)?;
let report = service.use_notes_root(synthetic_notes_dir)?; // builds/publishes immediately
let selected: Option<std::path::PathBuf> = service.notes_root()?;
let watcher = service.watch()?; // retain in application state
let hits = service.search("ledger")?;
let people = service.people()?;
let documents = service.documents()?;
```

The accessor is `notes_root(&self) -> Result<Option<PathBuf>>`: it reads current config under the shared lock and returns an owned canonical path, not a cached reference. A retained service and watcher follow changes made by another service or real CLI process using the same app-data directory.

`init_notes_root` is the only notes-writing operation in Phase 0 and accepts only empty/new directories. Other operations never rewrite sources. `index()` returns counts and warnings. Invalid UTF-8 and unreadable individual Markdown files remain plain document records with warnings; unreadable content never retains an old body/profile. An unreadable root is an error and does not wipe the previous index. Metadata comes from opened file handles so concurrent unlink does not abort a whole scan.

## Synchronization, recovery and Rust choices

Owned serializable values keep IPC/storage lifetimes simple. Optional profile fields and dates express missing data. Modification nanoseconds are decimal strings to avoid JSON/JavaScript integer precision loss. SHA-256 full scans catch offline edits even when mtimes are restored. Host-aware relative path components preserve legitimate Unix backslashes rather than turning them into directory separators.

One stable `store.lock` in canonical app data coordinates cooperating threads, instances and processes through an OS-backed exclusive lock. The guard covers current config discovery, full scans, publication and reads. Lock order is desktop session mutex (when applicable), store lock, then SQLite; watchers never take the desktop mutex. RAII closes the independent lock descriptor on success/error, and watcher sleep is outside the guard. Never replace or remove the lock file while an app is running, because that would split the lock domain.

Bundled SQLite provides FTS5 consistently. Each operation uses short-lived connections with a busy timeout. Indexed-root identity is committed in the same transaction as document, people and FTS rows. Config replacement occurs while that transaction is uncommitted, under the same OS guard: config-publication failure rolls back the SQL changes. A mismatch after interruption or a subsequent SQL commit failure is repaired before returning rows. Legacy indexes without identity rebuild on use. Recognized SQLite corruption and invalid serialized derived rows reset/rebuild the disposable index under the lock; config/notes are not deleted. Unrelated filesystem/permission errors remain errors. Arbitrary wrong-shape schemas require future schema-version handling; do not claim every SQLite failure is corruption.

The watcher polls metadata/structure about every 200 ms, including Unix ctime/inode/permissions, and reads/hashes note bodies when that snapshot changes. It does not hash the entire corpus at idle. Startup/explicit rebuild still use full content hashes. Dropping `WatchHandle` signals shutdown and joins the thread; `last_error()` reports the latest polling error. Existing watchers follow cross-process root changes. Reads can repair startup/root/index mismatches, but ordinary same-root source edits converge through the watcher; the BDD watcher tests do not manually index while polling.

Full scans and the shared lock can delay searches or root switches, and the current lock wait has no timeout. The two-second service-level target is tested on synthetic fixtures, not promised for arbitrary corpus sizes or stalled volumes. Large-corpus incremental indexing and bounded lock waits remain follow-ups.

## Configuration and source safety

`application_data_dir() -> Result<PathBuf>` resolves `TOPICS_APP_DATA_DIR` before OS discovery and creates nothing. Overrides must be nonempty absolute paths. The macOS default matches Tauri's identifier: `~/Library/Application Support/com.macsdickinson.topics`. An exported obsolete `TOPICS_APP_DATA` is an explicit error. On Unix, explicitly empty HOME without an override fails before OS fallback; unset HOME is normal OS behavior, not a test-isolation technique.

App data and notes must be disjoint trees. Initialization validates separation before creating the default layout and rejects parent traversal. Scanning does not follow source symlinks; a chosen root symlink is canonicalized. Foundation writes use app data; approved workspace writes additionally use the app-owned `topics/` records described below. Store creates no notes Git repository and makes no network requests. Concurrent source edits are observed on a later poll/full scan; warnings and watcher errors remain inspectable.

## Validation and test safety

`bash scripts/check.sh --core-only` runs formatting, locked warning-denied clippy/tests excluding the desktop package, and both Cucumber runners: 15 foundation and 20 workspace service scenarios. This is also the Ubuntu core CI scope, requiring no desktop GTK/WebKit build. `bash scripts/check.sh` uses the complete workspace and additionally runs Playwright and the real macOS embedded-provider WebdriverIO search and workspace suites. macOS CI invokes that full command with Rust 1.98.1, rustfmt/clippy and the pinned project-local Node runtime. Genuine Codex acceptance is an explicit synthetic-only opt-in, documented in `apps/desktop/README.md`. Core-only results alone do not establish desktop readiness.

Cucumber uses explicit Given/When/Then definitions and `fail_on_skipped`; unknown steps fail instead of being absorbed by a catch-all. Source-tree snapshots cover files, directories and symlinks with contents and metadata. Service/CLI tests cover recovery, root switching across processes, publication consistency, source permissions/unlink, path identity, query edge cases, watcher lifecycle/errors, profiles/aliases and config resolver safety. A bounded real-CLI test holds an external store-lock descriptor, confirms use/search cannot complete before release, then verifies successful new-root results. One isolated no-op-lock mutant confirms that test detects omitted locking; this is not a general mutation campaign.

All fixtures are temporary and synthetic. CLI subprocesses use an absolute synthetic app-data override or a fully synthetic valid HOME; native smoke always uses an absolute temporary override. Never copy real notes into fixtures, follow the repository's notes symlink, or launch tests against a personal configured root. Never probe empty/missing HOME through real OS discovery without an absolute safe override: use injected resolver inputs and a fallback closure that fails if called. Every spawned child/helper must have bounded waits and cleanup, including assertion failures. Do not mutate global environment/runtime defaults, submit note content to cloud services or infer product approval from passing tests. Follow the approved BDD red/green process when changing product behavior.

Current evidence and exact commands are linked from [review fixes](phase-0-review-fixes.md), [BDD evidence](phase-0-bdd-evidence.md) and [final checks](phase-0-final-checks.md). Hosted CI, live read-only verification and approval records remain manager-owned gates; these local results do not invent sign-off.

## Topic workspace service and runtime seam

`topics-core::workspace::*` (also re-exported at the crate root) is the canonical serde API. It owns the UUID/date/candidate shape checks; store owns reference resolution, selected-byte checks, Markdown records and journalling. Mutation objects reject unknown properties, including tagged unit variants; nullable properties must be present as JSON `null`. Field names remain snake_case. UI commands receive one object named `request`.

`WorkspaceService::open(absolute_app_data)` opens the same configuration and stable `store.lock` as Phase 0. Every operation discovers the current configured root under that lock. Explicit root selection rotates the root capability ID, including reselecting the same path; accepted Markdown knowledge remains, while old scopes and pending approvals are invalidated. Root partitions in app data hold immutable preview snapshots, run capabilities, pending proposals, snapshots and operation journals. No provider or runtime process is invoked by this crate.

The runtime host first calls `scope_preview(ScopePreviewRequest)`, obtains explicit human consent, then `analysis_start(AnalysisStartRequest)`. Its tools may use only `scope_read(ScopeReadRequest)` and `source_context(SourceContextRequest)`. Both require the service-generated root/scope/run IDs on every lookup. `validate_proposal(StageProposalRequest)` checks a buffered `propose_changes` tool call without publishing or consuming a capability; it shares the preparation and validation used by staging. After a successful terminal turn only, `stage_proposal` consumes that capability and creates a pending proposal. Errors/cancellation must call `run_cancel`; a consumed/cancelled capability cannot read or publish late results. The runtime never receives `proposal_decide`, root changes, human inventory, undo or write capabilities.

Human browsing uses `sources_list(RootRequest)` and `source_get(SourceGetRequest)`, including local-only sources without cloud consent. `statement_get(StatementGetRequest)` returns persisted correction/edit text and timestamp for the evidence UI. These are not model tools. Neither legacy Phase 0 search nor human inventory may be registered as a model retrieval tool. A fresh root needs no provider: `manual_propose(ManualProposeRequest)` creates a pending proposal and uses exactly the same human approval service.

The CLI mirrors those requests: `topics workspace <root-get|root-set|sources|source|statement|source-repair|preview|manual|proposals|decide|topics|topic|history|undo|sensitivity> 'REQUEST_JSON'`. It is a recovery/testing adapter, not another apply implementation. JSON errors include the canonical error code in their displayed message. CLI tests pass absolute synthetic `TOPICS_APP_DATA_DIR` values.

## Workspace records, evidence and write recovery

App-owned records use `topics/{topics,claims,connections,rules,sources,statements,unresolved,operations}/<uuid>.md`. Claim filenames use revision IDs. Each begins with YAML frontmatter containing `schema: topics/v1`, `record_kind`, `id`, `operation_id`, and `data: <typed JSON object>`; JSON is valid YAML flow syntax. The Markdown body gives a readable kind heading and assertion/name/text. This v1 parser deliberately accepts the documented five-property frontmatter and typed JSON data, rather than arbitrary hand-written YAML. Malformed committed payloads and duplicate IDs are reported. Current bytes must match the latest committed target, not merely any historical operation. A missing, edited or rolled-back target is a conflict: projections recover the latest committed payload from typed operation snapshots (or retained legacy journals) with warnings, while damaged source/topic mappings stay restricted. Source inventory never silently replaces damaged committed mappings or overwrites an untracked target. A mapping that cannot be reconstructed blocks model access until recovery. External source meeting bytes remain untouched.

Operation records are durable commit markers. Their data records ordered target paths, expected hashes/absence, new hashes, dependency IDs, tombstones, undo lineage, and original/applied proposal candidates. Accepted knowledge is reconstructed directly from committed Markdown; deleting SQLite/FTS and restarting loses no topics, claim history, connections, rules, statements or decisions. Pending proposals and run state are disposable. A canonical fingerprint normalizes safely corresponding provisional IDs/timestamps, including claim endpoints; current claim/connection dedupe preserves accepted identity and provenance independently of the candidate set. Known topic echoes can accompany new facts. Names alone cannot match a second person: unique identity matching also needs the same cited assertion or complete relationship evidence, and ambiguity remains reviewable. Case/whitespace and kind variants participate only in ambiguity detection. Topic-only collisions with selected passage evidence also receive unresolved review; a real second Joe can be explicitly accepted. Equivalent claims and connections within one pending model proposal union source evidence and uncertainty and remap dependent claim endpoints. A meaningful superseding revision retains its established logical assertion identity and supersedes list rather than a plain duplicate UUID; dependent remap chains resolve to the final retained identity. Equivalent revisions targeting different established logical assertions require separate review. A successful all-duplicate/suppressed result is accepted with zero candidates and no operation. Undo invalidates cached decisions for absent knowledge; fresh provisional IDs can propose it again. Pending proposals with changed dependencies or recovery conflicts become Conflict and cannot capture fresh analysis forever. Approval checks the actual edited/selected subset dependencies, not every indexed record or unrelated selected document. It also reuses the pure identity/dedupe/rule normalization against current knowledge under the commit lock; if another acceptance/correction changes the reviewed meaning, it reports Conflict and requires fresh analysis, rather than silently accepting duplicate or stale assertions.

Before the first target replacement, a flushed app-data journal stores every target's previous bytes or explicit absence (`old_bytes: null`) and staged bytes. File replacements use unique same-directory temporary files, flush, rename and parent-directory flush. All expected target hashes are checked, and the operation marker is written last; projections ignore uncommitted records. Restart resumes only when current target hashes match either expected or already-written new hashes. Otherwise, it preserves old, staged and current bytes and records a conflict, without publishing incomplete knowledge. Already replaced targets are restored only when their bytes still match this operation's staged hash, keeping previously accepted records visible; external versions are not overwritten. Empty/incomplete journals and the app's hidden temporary files do not brick reads/staging. Recovered commits reconcile proposal status without needing another approval click. Proposal conflicts additionally preserve the original reviewed record bytes and proposed Markdown. This is cooperative process coordination and recoverable per-file replacement, not cross-file atomic rename or protection against every race with an uncooperative editor.

Undo creates another committed operation. Dependency checks identify later live operations; creations get durable tombstones, while updates restore previous data under a new operation ID. Undo retains original records and operation history. An update can be undone before undoing its original creation. Compensating undo operations cannot themselves be undone; restore intended knowledge through a reviewed proposal instead. Snapshot recovery depends on retaining the root-partitioned app-data snapshots; the disposable SQLite database is independent.

Citations validate source ID, root-relative path, full-document SHA-256, UTF-8 byte boundaries, passage hash and exact excerpt. A changed or missing source is stale; it is never silently reanchored. Explicit human `source_identity_repair(SourceRepairRequest)` journals a mapping repair for rename/edit with expected source hash, restrictive sensitivity and dependency checks. It never changes old citation paths/hashes or source files; replacing stale evidence requires a separate reviewed revision. Date filtering uses validated filename dates first, then exact ISO `date:` frontmatter; absent/invalid dates are visibly excluded and mtime is never used as document date.

A correction cites its persisted user statement, supersedes the old revision, and records a deterministic topic/predicate/source-scoped suppression rule. Old transcript assertions remain in history; a rule suppresses false candidates but never accepts a replacement. Editing a pending assertion during human approval adds a persisted user-edit statement to its evidence in the same operation, retaining the original transcript only as context. Source/topic sensitivity is durable; latest same-path labels dominate older hashes and local-only evidence taints derived topics, including connection-only evidence. Selected paths resolve actual filesystem identities before policy, so APFS case aliases cannot bypass labels or the reserved app directory. Same-content relocation/copy retains restrictive or unresolved sensitivity until explicit review; this is bounded hash matching, not universal recognition of rewritten copies. Human consent is bound to path, content hash and operation sequence: an older destination label cannot release moved private bytes, and a decision about a stale source ID cannot grant access to the new occupant. A fresh human review of the current mapping can release its exact bytes. Source consent cannot override a private derived topic: topic taint is checked before source review, and preview visibly excludes the affected source while retaining unrelated eligible sources. Releasing that topic requires its explicit human declassification as well. Only root `topics/` is reserved; nested source directories such as `Projects/topics/` remain eligible. Model-supplied CloudAllowed becomes Unknown; explicit human sensitivity decisions grant access. Unknown confirmation remains per run and cannot lift local-only or damaged mappings.

The synthetic-only `topics-store/test-support` feature exposes a deterministic interruption seam used by BDD; normal application callers do not need it. Core validation runs are documented in `features/topic-workspace/evidence-core-green.md`; desktop and runtime-only scenarios require their owning streams' evidence.

When running the store integration tests without the BDD workspace member, enable that feature explicitly: `cargo test -p topics-store --features test-support`. For a combined runtime/setup/store run, use `cargo test -p topics-runtime -p topics-setup -p topics-store --features topics-store/test-support`. The full workspace check enables it through the BDD dependency.

## Reviewed model publication and evidence boundaries

The runtime-independent `stage_proposal_guarded(request, publisher)` seam performs all blocking validation, canonicalization, run consumption, JSON serialization and temporary-file flush before invoking `publisher(&proposal, &mut action)`. The action makes final pending/no-change cache visibility through an idempotent rename. The runtime supplies its deadline/revocation permit around that action and records the published IDs; ordinary `stage_proposal` uses unconditional publication. Existing duplicates and accepted empty outcomes also traverse the gate. Denial drops the hidden temporary file without creating a pending record. Pending cache directory durability is best effort outside the gate; accepted knowledge retains the full journal/commit-marker durability protocol. Validation-only tool calls still publish nothing and consume no run. Cloud-boundary checks inspect only submitted IDs; a name-independent dependency validation pass runs before server identity lookup. Server-derived ambiguity, including private alternatives, is for the human inbox only. Ambiguous claims propagate human-only status through both logical and revision endpoint IDs to dependent connections; suppressed claims prune their dependents. Already declared unresolved alternatives stay stable during human approval regardless of UUID order. As an accepted bounded limitation, model-declared alternatives are preserved rather than augmented: a declared list may omit a server-known private alternative from the human inbox. That list is not an exhaustive identity catalog; model validation remains uniform and private alternatives are not exposed to model context. The model validation result is unit success or a raw-input error; adapters must never serialize human proposal candidates, private alternatives or their counts as model tool output. Raw model payloads keep their 200-candidate/2 MiB limit; a bounded server-derived ambiguity record may accompany each topic in human review.

Current human-supported values for an explicitly authorized CloudAllowed topic can be returned when original evidence is outside scope, with all excluded passage/source/path/superseded identifiers removed and a redaction warning. History stays strictly scoped; unrequested statement text is absent. Value authority requires a human change to the value proved by durable original/applied operation data, or a raw statement tied to an actual changed-value revision or whose entire trimmed text exactly equals the entire trimmed claim value. Substring, token-boundary and semantic guesses do not grant literal authority, even after candidate approval. Same-value metadata follow-ups can retain authority from an earlier human-authorized revision of that same logical assertion, subject and predicate; a visited-set traversal examines at most 100 revisions and never crosses a changed value to revive old transcript authority. A raw question or metadata-only statement cannot authorize an unchanged transcript value. No-op corrections with identical matched/replacement values are rejected. Subject-only, uncertainty-only or other metadata edits retain their exact UI provenance but do not declassify the unchanged transcript value. Connection source endpoints must be selected, claim endpoints must have scoped evidence, and topic endpoints must remain nonprivate; human topic browsing retains complete endpoints. Source/topic taint and current path labels are checked before redaction, so redaction cannot declassify private values. Context filtering reads only selected passages; human citation browsing remains a separate service. Analysis adapters must request context only for topics tied to selected eligible evidence, never export the complete human inventory.

Editing a claim's subject or uncertainty now records the full before/after human assertion just as a value edit does, preserving the requested uncertainty and attaching a persisted statement. A connection edit retains the original passage as context and visibly qualifies the relationship as HUMAN-EDITED, with a persisted statement when a topic endpoint is available and exact original/applied assertions in durable operation metadata otherwise. Deterministic rules remain exact predicate/value matches; a plain edit does not invent an implicit future suppression rule.

Legacy FTS is a human source-search feature, not an MCP tool: it continues to search the user's selected source notes, including their private sources, while excluding every case spelling of root app-owned `topics/` records. Generated private/undone assertions, statements and operation snapshots are therefore not mistaken for source search hits. Model tools remain the bounded scope/context surface only.

Operation sequences order new commits independently of wall-clock changes. Coordination still assumes cooperating callers share one app-data store lock; two independently configured app-data directories writing one root are outside that guarantee. Existing legacy markers use their historical ordering until newer sequenced writes. No real power-loss campaign or universal copy-secrecy claim was made. Wholesale removal of all later Markdown metadata plus all app-data history cannot be distinguished from a genuinely older root snapshot; surviving markers/journals detect the tested missing/rollback cases. A surviving orphan correction or rule whose operation marker and app-data journal are both absent triggers a recovery warning, withholds the superseded current assertion and restricts its topic context; it never accepts the orphan replacement. Known staged/conflict journals retain ordinary recovery semantics. Restore the missing committed history to recover that topic. Conservative private-history taint may require explicit source/citation review. All independent-review fixes and exact evidence are recorded in `features/topic-workspace/evidence-core-review-fixes.md`; initial green evidence is not a substitute for independent acceptance. The bounded second review corrections and RED/GREEN record are in `features/topic-workspace/evidence-core-rereview-fixes.md`; narrower final confirmation counterexamples and corrections are recorded in `features/topic-workspace/evidence-core-final-confirmation.md`. The final strict equality policy and same-value authority lineage evidence are in `features/topic-workspace/evidence-core-authority-final.md`. Residual limits include a moved file whose private bytes are edited before inventory (hash lineage cannot identify the altered copy), Unicode NFC/NFD name variants, and logical claim endpoint revision selection exposing only an opaque ID/relation; these were explicitly left outside the bounded final correction scope.
